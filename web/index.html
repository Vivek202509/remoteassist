Remote support so easy

Remote control to support your clients and colleagues from anywhere — with the controlled device always in charge of what happens.

Safe remote control

Nothing starts without a tap on the controlled device. A persistent notification stays up for the whole session, and either side can end it instantly.

Works both ways

Every install ships both roles. Whichever device opens the session is the one being controlled — so the same app supports you and your partner.

Cryptographic pairing

Authenticated ECDH plus a short safety number you compare out loud once. Trust is stored encrypted on both devices, keyed to a hardware-backed P-256 identity.

MITM-proof media

Each peer signs its DTLS fingerprint with its identity key and verifies the other’s. A compromised signaling server still cannot insert itself into the stream.

Unattended access

Owner-configured grants that are scoped, expiring and revocable, referencing a paired identity. Android caps how far this can go, and the documentation says exactly where the ceiling is.

Survives network switches

Wi-Fi to cellular triggers an ICE restart on the same peer connection: no black screen, no second consent prompt, exponential backoff if the path is slow to return.

Wake a sleeping device

Dialling an offline host sends a high-priority data-only push; the join request is queued and delivered the moment that device reconnects. Needs your own Firebase project — it is off by default and everything else works without it.

Your broker, your rules

Run the Node.js signaling broker and coturn yourself. It brokers codes and relays the handshake — it never sees a frame of your screen.

Four steps

How a session works

No account, no cloud dashboard, no port forwarding.

Install

Put the app on both devices and point them at your broker URL — the same build acts as host or controller.

Pair once

Compare the safety number the two devices show. From then on each side knows the other’s public key.

Share the screen

The host taps Share my screen and reads out the six-digit code, valid for five minutes.

Control

The controller enters the code, the host allows it, and taps and swipes travel over the encrypted data channel.

Security model

Designed to be verifiable

Each guarantee below maps to code you can read, not a promise on a marketing page.

Hardware-backed identity

Every device generates a P-256 keypair inside the platform keystore. The public key is the device id, so identity cannot be spoofed by renaming a device.

Verified pairing

Authenticated ECDH plus mutual identity proofs, confirmed by a safety number compared out of band. Trust is persisted in encrypted storage.

Per-session authorisation

The dialling side signs a fresh challenge for every session. Only an already-trusted identity is accepted — a stolen device id is not enough.

Signed media fingerprints

DTLS fingerprints are signed with the identity key and verified against the paired public key, so a hostile broker cannot become a silent middlebox.

Visible, revocable consent

Attended sessions need an explicit tap and the system capture prompt. Unattended grants are scoped, expiring and revocable at any time from the device.

The broker sees no media

Signaling carries only setup metadata. Where TURN is needed, the relay forwards packets it has no key to read.

Read the details: threat model, protocol specification and architecture notes are in the repository.

Questions

Frequently asked

Does my screen go through your servers?
No. Media is peer-to-peer WebRTC, encrypted with DTLS-SRTP. The signaling broker relays only connection-setup metadata. If the two networks cannot reach each other directly, a TURN relay forwards encrypted packets it cannot decrypt.
Do I have to install something on the controlled device?
Yes — the same app, which contains both roles. Screen capture and input injection require platform permissions that a web page cannot obtain.
Can I run it with no servers of my own?
Not today. You need the signaling broker running somewhere both devices can reach, and coturn is strongly recommended because carrier CGNAT usually blocks direct peer-to-peer. Both are in the repository with configuration files.
Is unattended access truly unattended on Android?
Partly. Android 11+ makes a capture permission grant effectively single-use, and Android 14+ tightens re-acquisition further. A production unattended build must keep the capturer alive across sessions rather than replaying a stored grant. That is a platform ceiling, and we document it rather than paper over it.
Is there an iPhone version?
No. iOS does not expose the APIs needed to inject input into another app, so a controlled iOS device is not possible outside of Apple’s own frameworks.
Is it really free?
The source is MIT licensed — use it commercially, fork it, audit it. Nothing is for sale today: there is no paid tier, no trial and no price list.
Can I use it in production?
Not yet, and the site will say so until that changes. The code is complete on Android and its automated tests pass, but no session has been observed between two physical devices and no session has crossed a network through TURN. Until those are recorded in the test matrix, treat RemoteAssist as something to build, read and evaluate.
