Status & naming

What state is this in? The signaling broker runs and is covered by 229 protocol conformance checks and 46 broker checks that pass on any machine. The Android app is feature-complete and its unit tests pass. The Windows host is a preview. RemoteAssist has not yet been observed running between two physical Android handsets. The code is complete and its unit tests pass; the device acceptance matrix in the repository is still entirely open.

Not yet Internet-ready remote control. TURN has not been exercised from Windows, and no cross-network session has been recorded on any platform. RemoteAssist is not yet demonstrated as Internet-ready remote control. Every claim on this site is traceable to the cross-platform test matrix and the real-device matrix.

RemoteAssist and Techee are the same thing

RemoteAssist is the product name — the Android application id (com.remoteassist), the website, and how the system is described publicly. Techee is the internal project name, and it is what you will meet inside the repository: the working directory, the .NET solution Techee.Windows.slnx, and the cryptographic transcript prefixes the protocol pins, such as techee-register-v1 and techee-sdp-v1. Those strings are signed and verified across three language implementations, so they are deliberately not being renamed: changing them would break compatibility for no user-visible gain. One product, two names, and this paragraph is the only place the site explains it.

Quick start

Three moving parts: the broker (always), coturn (whenever the two devices are not on the same network), and the app on each device.

  1. Start the broker on a machine both devices can reach.
  2. Build and install the app on both devices, pointing them at that broker.
  3. Pair them once and compare the safety number.
  4. On the device to be controlled, tap Share my screen; enter the code on the other one.
# broker
cd server && npm install && npm start

# app (in another shell) — point it at a broker the phones can reach
cd android && ./gradlew :app:assembleDebug -PsignalingUrl=ws://192.168.1.43:8080

On a LAN? Use your machine’s address, not localhost — ws://192.168.1.43:8080 style. Phones cannot reach your loopback interface, and the debug default ws://10.0.2.2:8080 is the emulator’s alias for it, so a handset built without -PsignalingUrl never connects.

Running the broker

The broker is a WebSocket router with in-memory state. It:

  • registers devices by their public-key id, after verifying a signed challenge;
  • brokers code joins (host-open → six-digit code → join) and paired-direct dials to a trusted host id;
  • relays offer, answer, ice and restart, plus the pairing messages;
  • issues TURN credentials as an HMAC of an expiry against the coturn shared secret;
  • queues a join for an offline host and sends a wake push, if FCM is configured.

An unauthenticated socket may send only register and register-proof; everything else is rejected until identity is proven. State is deliberately in memory — restart the broker and live sessions simply re-establish.

Behind a reverse proxy, terminate TLS and forward the WebSocket upgrade:

location /ws {
  proxy_pass http://127.0.0.1:8080;
  proxy_http_version 1.1;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection "upgrade";
  proxy_read_timeout 300s;
}

TURN & NAT traversal

STUN alone works on a shared Wi-Fi network. Across mobile carriers it usually does not: CGNAT prevents a direct path, so you need a relay. Install coturn on a host with a public IP, copy infra/turnserver.conf, and make sure its static-auth-secret is identical to the broker’s TURN_SECRET — that shared secret is what makes the broker’s short-lived credentials valid.

Ports coturn needs open.
PortProtocolWhy
3478UDP + TCPSTUN / TURN
5349UDP + TCPTURN over TLS/DTLS
49152–65535UDPRelay port range

Credentials expire — by default after an hour — and are re-fetched automatically when a session recovers, so a long call does not fail on a stale username.

Pairing two devices

Each device holds a P-256 keypair generated inside the platform keystore; the public key is the device id. Pairing performs an authenticated ECDH, exchanges identity proofs, and shows both people a short safety number.

Compare that number out loud. If the two devices show different numbers, someone is in the middle — stop. Once confirmed, the trust record is written to encrypted storage on both sides, and from then on every session requires a signature from that exact key.

Attended sessions

An attended session is the normal case: someone is holding the controlled device.

  1. The host taps Share my screen. The broker returns a six-digit code, valid five minutes.
  2. The controller enters it. The host sees a consent dialog naming the paired device.
  3. On Allow, Android shows its own screen-capture prompt. Both are required — the app cannot skip either.
  4. Capture runs as a foreground service with a notification that cannot be dismissed while the session is live.
  5. Taps and swipes arrive over the WebRTC data channel and are injected by the accessibility service, normalised to the host’s screen geometry.
  6. Either side ends the session; the notification clears and the peer connection closes.

Both roles ship in every install, so A→B and B→A are two independent sessions — whichever device ran host-open is the controlled one.

Unattended access

An unattended grant is created by the device owner, on that device. It is scoped to a paired identity, carries an expiry, and can be revoked at any time. There is no server-side switch that can conjure access to a device that never granted it.

Platform ceiling, stated plainly. On Android 11+ a MediaProjection permission intent is effectively single-use, and Android 14+ tightens re-acquisition further. The stored-intent approach in UnattendedHostService is a scaffold; a production unattended build has to keep the capturer and track alive across sessions instead. This is an OS constraint, not a missing line of code.

Reconnection

Recovery is armed the moment the first connection succeeds. A network-change callback or a DISCONNECTED / FAILED state triggers an ICE restart on the same peer connection: signaling reconnects if needed, TURN credentials refresh, and a new offer goes out with the ICE-restart flag. The video track and the data channel survive, so there is no black screen and no second consent prompt.

Backoff is exponential, capped at 15 seconds, six attempts. After that the session closes and the UI offers a manual retry.

Implemented, not yet observed. The recovery path is unit-tested, but no recorded session has been interrupted by a real network change on real hardware. Read it as a design that is built, not as a behaviour that has been timed.

Protocol reference

The wire protocol is specified with cross-language fixtures so the Android and Windows implementations cannot drift apart silently. The broker enforces it, and 229 conformance checks run in CI against the JavaScript implementation, with the Kotlin and C# suites held to the same fixture files.

The signaling messages a device exchanges with the broker.
MessageFromMeaning
register / register-proofdeviceClaim an identity, then prove it by signing a challenge
host-openhostOpen a session and receive a six-digit code
joincontrollerJoin by code, or dial a trusted host id directly
join-requestbrokerAsk the host for consent
offer / answer / icepeersWebRTC handshake, relayed verbatim
restartpeersICE restart after a network change
ice-serversbrokerTime-limited STUN/TURN credentials

Troubleshooting

The app never connects to the broker
Check the URL scheme (ws:// on a LAN, wss:// in production) and that the phone can reach the host — open http://<host>:8080 in the phone’s browser; a failed WebSocket upgrade still proves reachability. Cleartext ws:// to a non-loopback address needs a network-security config exception, which the debug build ships.
Code accepted, but the screen stays black
Almost always the capture prompt was dismissed, or the foreground service was killed by a battery optimiser. Exempt the app from battery optimisation on the host device and watch adb logcat for the capture service starting.
It works on Wi-Fi but not on mobile data
That is the classic missing-TURN symptom. Confirm coturn is reachable on 3478/5349, that the shared secret matches, and that the ICE candidate list actually contains typ relay entries.
Taps do nothing on the host
The accessibility service is not enabled, or was disabled by the system after an update. Re-enable it in Android settings; the app surfaces its state on the diagnostics screen.
Safety numbers do not match
Do not continue. Delete the pairing on both devices and pair again on a network you trust. A mismatch is the one signal the design gives you that something is intercepting.

Privacy & data

  • Media never reaches a server. Screen frames and input travel peer-to-peer under DTLS-SRTP. A TURN relay, when needed, forwards packets it cannot decrypt.
  • The broker stores connection metadata only, in memory: device id, socket, pending codes and grants. Restarting it erases that.
  • No analytics, no crash reporting, no advertising identifiers are collected by the app.
  • You own the deployment. Self-hosting means there is no third party to trust with session metadata either.

If you publish a build, the ready-to-paste store declarations are in play_console_declarations.md.
